1. Цель и позиционирование
Fullstack-приложение для управления задачами на канбан-доске с реалтайм-синхронизацией. Цель — показать работодателям навыки бэкенда (транзакции, конкурентность, WebSocket, аутентификация) в связке с сильным фронтендом.

В скоупе (MVP): регистрация/логин, доски у пользователя, колонки и карточки, drag&drop с сохранением порядка, реалтайм через WebSocket, шаринг доски по ссылке с ролями.

Вне скоупа (v2+): вложения файлов, комментарии, упоминания, уведомления, офлайн-режим.

3. Модель данных (Postgres)
sql
users         (id, email, password_hash, name, created_at)
boards        (id, title, owner_id → users, created_at)
board_members (board_id → boards, user_id → users, role enum('editor','viewer'), PK(board_id,user_id))
columns       (id, board_id → boards, title, position numeric, created_at)
cards         (id, column_id → columns, title, description, position numeric,
               created_by → users, created_at, updated_at, version int)
Ключевые решения:

position numeric, а не int: вставка между карточками — среднее (posA + posB) / 2, без переписывания колонки. Периодическая ребалансировка в фоне при плотных значениях.

version int в cards/columns — для оптимистичных блокировок.

Индексы: cards(column_id, position), columns(board_id, position).

Каскадное удаление: доска → колонки → карточки (ON DELETE CASCADE).

4. REST API
Префикс /api, защищённые — Authorization: Bearer <token>.

text
POST   /auth/register | /auth/login | /auth/refresh | /auth/logout
GET    /auth/me

GET    /boards                    POST /boards
GET    /boards/:id                PATCH/DELETE /boards/:id
POST   /boards/:id/share          POST /boards/join   { shareToken }

POST   /boards/:boardId/columns   PATCH/DELETE /columns/:id

POST   /columns/:columnId/cards   GET/PATCH/DELETE /cards/:id
POST   /cards/:id/move            { toColumnId, beforeCardId, afterCardId, expectedVersion }
/move — отдельный эндпоинт, потому что это транзакция: сменить column_id + вычислить position + проверить версию соседей (SELECT ... FOR UPDATE). Возвращает карточку + новую версию; при конфликте — 409.

5. Конкурентность и реалтайм
Оптимистичные блокировки: клиент присылает expectedVersion; бэкенд делает UPDATE ... WHERE id = ? AND version = ?. Ноль строк → 409 Conflict. Клиент при 409 подтягивает актуальное состояние по WS.

WebSocket (Socket.IO), комнаты по boardId:

Сервер → клиент:

text
board.joined, column.created/updated/deleted,
card.created/updated/moved/deleted, presence.updated
Клиент → сервер: board.subscribe, board.unsubscribe.

Правила:

Авторизация WS в handshake; при subscribe проверять членство в доске.

Клиент не фиксирует свои изменения локально «навсегда»: отправляет REST → состояние обновляет по WS-событию (оптимистичный UI + откат при ошибке).

В MVP — один инстанс бэка; Redis pub/sub адаптер — только в v2.


6. Этапы разработки
Скелет (1–2 дня): Postgres + миграции, auth, CRUD досок и колонок (без реалтайма и dnd).

Карточки и порядок: CRUD карточек, position, /move в транзакции, тесты на move (включая параллельный).

Фронт-доска: vue-draggable-plus, оптимистичные обновления, откат.

Реалтайм: Socket.IO, комнаты, события, синхронизация двух вкладок.

Шаринг и права: share-токены, роли, проверки доступа во всех эндпоинтах и в WS.

Полировка: ребалансировка позиций, presence, обработка 409 в UI, e2e на два клиента.

Критерии готовности MVP:

Два пользователя в двух браузерах видят изменения < 500 мс.

Одновременное перемещение не теряется (409 + консистентное состояние).

Viewer не может редактировать (ни REST, ни WS).

Порядок сохраняется после перезагрузки.

Удаление доски каскадно чистит данные.


7. Советы по разработке
Самая ценная часть для обучения — транзакция в /move. Напишите тест: 50 параллельных перемещений в одну колонку, проверьте отсутствие дублей позиций.

Тест на оптимистичную блокировку: два клиента с одной version → второй получает 409.

Тест на WS-авторизацию: подключение к чужой доске должно отбиваться.

Ребалансировка: скрипт, переписывающий position в целые 1..n, когда разница между соседями < epsilon.

Не переусложняйте: один процесс, REST вместо GraphQL, никаких микросервисов.
